Что такое вайб-кодинг?

«There's a new kind of coding I call "vibe coding", where you fully give in to the vibes, embrace exponentials, and forget that the code even exists.»
— Andrej Karpathy, 2 февраля 2025, X (Twitter)
Определение

Парадигма разработки, при которой инженер описывает намерение на естественном языке, а ИИ генерирует, тестирует и итерирует код. Человек переходит от написания кода к управлению процессом его создания.

Ключевой сдвиг

Код перестаёт быть основным артефактом работы. Основными артефактами становятся спецификации (PRD), правила (Rules), навыки (Skills) и архитектурные решения.

Эволюция парадигмы

2023–2024
Copilot-эра
Автодополнение кода. Человек пишет, ИИ подсказывает. Ответственность полностью на инженере.
2025
Vibe Coding
Описал → получил → запустил. Подходит для прототипов и демо. Контроль качества — опционален.
2025–2026
Agentic Coding
ИИ-агенты автономно анализируют, планируют, пишут, тестируют и итерируют. Структурированный процесс с обратной связью.
2026+
Agentic Engineering
Production-grade: PRD-driven, rule-bounded, с HITL и checkpoint-ами. Инженер = архитектор + оркестратор + ревьюер.
Три столпа Agentic Engineering
  • Autonomy — агенты принимают решения о реализации самостоятельно
  • Context — агенты анализируют код, зависимости, системные требования
  • Control — guardrails гарантируют безопасность и compliance
Критический разрыв: Вайб-кодинг без структуры = технический долг. Agentic Engineering = вайб-кодинг + дисциплина.

PRD — контракт на результат

Product Requirements Document — центральный артефакт agentic engineering. Определяет не как реализовать, а что должно быть достигнуто и когда задача считается завершённой.

PRD-Driven Agent Loop

Итеративный паттерн выполнения PRD агентом (также известный в сообществе как «Ralph Wiggum Loop»):

  • Написать PRD с чеклистом критериев «done»
  • Агент декомпозирует через TodoList
  • Выполнение пунктов + checkpoint на каждом шаге
  • Верификация: тесты, lint, code review
  • Цикл до полного завершения чеклиста
# PRD: Feature — User Authentication

## Objective
JWT-based authentication with OAuth2 support.

## Acceptance Criteria
- [ ] Login endpoint returns JWT token
- [ ] Token refresh mechanism (15 min TTL)
- [ ] OAuth2 flow for Google, GitHub
- [ ] Rate limiting: 5 attempts / minute
- [ ] Session invalidation on password change

## Constraints
- No session cookies (SPA-only)
- bcrypt for password hashing (cost=12)
- All endpoints return RFC 7807 errors

## Out of Scope
- MFA (separate PRD)
- SSO enterprise (Phase 2)
PRD ≠ ТЗ. PRD для агента — это исполняемая спецификация с чётко определёнными критериями завершённости.

Rules — конституция проекта

Rules — это неизменяемые ограничения, которые действуют на каждом шаге работы агента. Они формируют «конституцию» проекта и определяют, что агенту позволено и запрещено.

Типы правил в Cursor
  • Project Rules — .cursor/rules/, version-controlled, привязаны к кодовой базе
  • User Rules — глобальные для IDE, персональные настройки
  • Team Rules — командные правила (Team/Enterprise)
  • AGENTS.md — альтернативный формат, всегда загружается при старте
Скоупинг правил
  • alwaysApply: true — действует всегда
  • globs: **/*.ts — при работе с файлами
  • По запросу — через @-упоминание
  • Интеллектуально — агент решает сам
# .cursor/rules/api-standards.mdc
---
description: API coding standards for backend
globs: src/api/**/*.ts
alwaysApply: false
---

# Error Handling
All API errors MUST use RFC 7807 format.
Never expose stack traces in production.

# Validation
Use Zod schemas for ALL input validation.
Validate at the controller boundary, not in
service layer.

# Naming
- Endpoints: kebab-case (/user-profiles)
- Handlers: camelCase (getUserProfile)
- DB columns: snake_case (created_at)
Rules vs Skills: Rules — всегда активны (конституция). Skills — подключаются по запросу (экспертиза). Не путайте.

Rules — глубже

4 типа правил

Тип Когда активируется Расход контекста
Always Apply Каждый промпт, каждый файл Высокий — постоянный
Auto Attached При открытии файлов по glob-паттерну Средний — по файлу
Agent Requested Агент решает сам по description Низкий — on-demand
Manual Только при @-упоминании Минимальный
Лимит: Жёсткого ограничения на количество .mdc-файлов нет, но каждое always-apply правило на ~100 строк съедает ~500–1000 токенов. 5 таких правил = 2500–5000 токенов до начала диалога. Контекстное окно — 200K токенов; rules конкурируют с кодом и историей чата.

Бюджет правил для проекта

Рекомендация
  • Always Apply: 1–3 правила, суммарно < 150 строк
  • Auto Attached: 5–15 правил по glob-паттернам
  • Agent Requested: без ограничений (загружает description)
  • Manual: без ограничений
Типичная структура 
.cursor/rules/
├── project-core.mdc      # alwaysApply: true
├── typescript.mdc         # globs: **/*.ts
├── react-components.mdc   # globs: src/components/**
├── api-standards.mdc      # globs: src/api/**
├── testing.mdc            # globs: **/*.test.*
├── database.mdc           # globs: src/db/**
└── deployment.mdc         # agent requested
Приоритет загрузки

Team Rules → Project Rules → User Rules → Legacy (.cursorrules). При конфликте побеждает более высокий приоритет.

Skills — подключаемые компетенции

Skills — это on-demand загружаемые инструкции для агента. В отличие от Rules (всегда в контексте), Skills загружаются только когда нужны, экономя контекстное окно.

Структура SKILL.md 
skills/
└── python-testing/
    ├── SKILL.md        # Обязательно: инструкции
    ├── reference.md    # Опционально: детали
    └── examples.md     # Опционально: примеры
Принцип Progressive Disclosure

SKILL.md < 500 строк — только суть. Детали — в отдельных файлах с ссылками на 1 уровень вглубь. Каждый токен конкурирует за контекст.

Roles — эволюция роли инженера

Было: Developer
  • Пишет код руками
  • Отлаживает построчно
  • Ручной code review
  • Знание = API + синтаксис
Стало: Vibe Coder
  • Формулирует промпт
  • Принимает/отклоняет результат
  • Патчит edge cases
  • Знание = формулировка intent-а
Должно быть: Agentic Engineer
  • Пишет PRD и Rules
  • Проектирует архитектуру
  • Оркестрирует субагентов
  • Ревьюит и верифицирует
  • Управляет checkpoints

Роли агента в IDE

Modes
  • Agent Mode — полный доступ ко всем инструментам, реализация
  • Plan Mode — read-only, проектирование подхода, обсуждение trade-offs
  • Ask Mode — read-only, исследование кода, ответы на вопросы
  • Debug Mode — систематическая отладка с runtime-доказательствами
Senior-инсайт: Переключение между режимами — не UI-фича, а архитектурный приём. Plan Mode перед Agent Mode существенно снижает число итераций на сложных задачах за счёт раннего выявления trade-offs.

Roles для Frontend Developer

Помогают

Rules и Skills, которые нужны

  • React/Next.js patterns — Server Components vs Client, App Router conventions
  • TypeScript strict — noImplicitAny, proper generics, type inference
  • Component structure — PascalCase, co-located styles, barrel exports
  • State management — Zustand/Jotai patterns, no prop drilling > 2 levels
  • Testing skill — @testing-library/react, MSW для mocking API
  • Accessibility — ARIA roles, semantic HTML, focus management
  • CSS conventions — Tailwind utility order, design tokens
Пример rule для React 
# .cursor/rules/react.mdc
---
description: React component patterns
globs: src/components/**/*.tsx
alwaysApply: false
---
- Use functional components only
- Extract hooks > 10 lines into custom hooks
- Props interface named {Component}Props
- No default exports for components
- Error boundaries on route level
Мешают

Rules и Skills, которые вредят

  • Backend-specific rules в alwaysApply — SQL conventions, ORM patterns загружаются на каждый промпт, тратят контекст впустую
  • Избыточные style guides — копирование всего Airbnb ESLint guide в правило; агент и так знает стандарты
  • Rules про CI/CD — deployment, Docker, Terraform — irrelevant при работе с .tsx файлами
  • Overscoped always-apply — «Всегда используй PostgreSQL» при работе с UI-компонентами
  • Conflicting state rules — «Используй Redux» + «Используй MobX» в разных правилах
  • Устаревшие patterns — Class components, HOC вместо hooks, getInitialProps
Оптимальный набор Rules для Frontend 
.cursor/rules/
├── project-core.mdc      # always: stack, monorepo
├── react-patterns.mdc     # glob: **/*.tsx
├── typescript-strict.mdc  # glob: **/*.{ts,tsx}
├── styling.mdc            # glob: **/*.{css,tsx}
├── testing.mdc            # glob: **/*.test.*
└── a11y.mdc               # agent-requested
# Итого: 1 always + 4 glob + 1 agent = 6 rules

Subagents — делегирование и специализация

Subagents — специализированные агенты, работающие в изолированном контексте. Основной агент делегирует задачи через task tool, получая обратно только финальный отчёт.

Встроенные в Cursor
  • Explore — поиск по кодовой базе, глобы, grep
  • Shell — выполнение bash-команд
  • Browser — навигация и тестирование в браузере
  • General Purpose — универсальный, наследует инструменты
Наследование
  • General Purpose — наследует tools и config родителя
  • Custom subagents — НЕ наследуют skills. Указывать явно
Subagents stateless! Каждый вызов — чистый контекст. Полные инструкции в одном промпте. Нельзя полагаться на историю предыдущих вызовов. 
# Кастомный субагент в Deep Agents
agent = create_deep_agent(
    subagents=[
        {
            "name": "researcher",
            "description": "Research and compile findings",
            "system_prompt": "Search thoroughly, 
                              return concise summary",
            "tools": [search_papers, web_search],
            "skills": ["/research-skills/"],
        },
        {
            "name": "code-deployer",
            "description": "Deploy code to prod",
            "tools": [run_tests, deploy],
            "interrupt_on": {
                "deploy": True  # HITL!
            },
        }
    ],
    checkpointer=MemorySaver()
)
Skills не наследуются субагентами автоматически — указывайте явно через skills параметр.

Checkpoints — точки восстановления

Checkpoints — механизм сохранения состояния, позволяющий откатить, форкнуть или путешествовать по истории выполнения. Работают на двух уровнях.

Уровень 1: Git Checkpoints
  • Коммит перед каждой значимой операцией ИИ
  • WIP-коммиты как точки отката
  • git restore для безопасного возврата
  • Auto-commit на feature-ветках (опционально)
  • Squash перед merge в main
Уровень 2: Agent Checkpoints
  • Checkpointer сохраняет состояние на каждом super-step
  • thread_id — идентификатор последовательности
  • Time Travel — просмотр и откат к любому шагу
  • Fork — ветвление от прошлого состояния
  • InMemorySaver → dev, PostgresSaver → prod

Workflow с точками восстановления

1. git commit -m "WIP: before auth"
↓
2. Агент реализует фичу (автоматический checkpointing состояния)
↓
3. Верификация: тесты, ревью, lint
↓ Проблема?
4a. git restore → откат к WIP-коммиту
4b. graph.get_state_history() → time travel к шагу агента
Правило: Нет коммита перед ИИ-операцией = нет точки отката. Checkpoint дешевле переделки.

HITL — человек в контуре

Human-in-the-Loop — паттерн, при котором агент приостанавливает выполнение перед критичной операцией и запрашивает решение человека.

Три решения
  • Approve — подтвердить и продолжить
  • Edit — модифицировать аргументы, затем выполнить
  • Reject — отклонить с обратной связью
Когда использовать
  • Запись в БД, удаление данных
  • Деплой в production
  • Отправка email/уведомлений
  • Compliance-чувствительные операции
  • Модификация инфраструктуры
# Конфигурация HITL
agent = create_deep_agent(
    interrupt_on={
        "write_file": True,
        "execute_sql": {
            "allowed_decisions": 
                ["approve", "reject"]
        },
        "read_file": False,  # Без HITL
    },
    checkpointer=MemorySaver()  # Обязателен!
)

# Resume после одобрения
result = agent.invoke(
    Command(resume={
        "decisions": [{"type": "approve"}]
    }),
    config=config
)
Требования: HITL без checkpointer = ошибка. HITL без thread_id = невозможно возобновить. Оба — обязательны.

Middleware и TodoList

Middleware — перехват и контроль

Middleware перехватывает цикл работы агента на заданных точках. Deep Agents используют явный middleware layer (в отличие от LangGraph, где это ручная проводка).

Middleware Назначение Вкл.
TodoList Планирование задач ✓
Filesystem Файловые операции ✓
SubAgent Делегирование ✓
Skills On-demand знания Opt-in
Memory Долгосрочная память Opt-in
HITL Утверждение Opt-in

TodoList — декомпозиция задач

Агент автоматически декомпозирует сложные задачи в управляемый список через write_todos. Статусы: pending → in_progress → completed. 

# Агент автоматически планирует:
write_todos([
  {"content": "Design data models",
   "status": "in_progress"},
  {"content": "Implement CRUD endpoints",
   "status": "pending"},
  {"content": "Add authentication",
   "status": "pending"},
  {"content": "Write tests",
   "status": "pending"},
])
Custom middleware хуки: before_model, after_model, wrap_tool_call, before_agent, after_agent — полный контроль пайплайна.

Memory — модель памяти агента

Краткосрочная

StateBackend

  • Живёт в рамках thread
  • Теряется при завершении
  • По умолчанию
  • Рабочие файлы, черновики
Долгосрочная

StoreBackend

  • Персистентна между threads
  • Требует Store instance
  • Предпочтения, факты
  • InMemoryStore → dev
  • PostgresStore → prod
Гибридная

CompositeBackend

  • Маршрутизация по путям
  • /draft/ → ephemeral
  • /memories/ → persistent
  • Longest prefix match
Ключевое различие: AGENTS.md (всегда в контексте) ≠ Skills (on-demand) ≠ Store (cross-session). Неправильный выбор модели памяти — причина деградации качества на длинных сессиях.

3+ крупных каталога, но нет единого формата обмена. .mdc (Cursor) ≠ .windsurfrules ≠ CLAUDE.md. PRPM.dev пытается стать универсальным npm для AI-правил с поддержкой Cursor, Claude, Windsurf и Copilot.

GitAgent — попытка объединить всё

Docker-подобная спецификация: agent.yaml (манифест), SOUL.md (личность), DUTIES.md (обязанности), skills/, rules/, memory/. Определи агента один раз — экспортируй в любой фреймворк.

Прогноз: Skills уже стандартизованы. Rules — следующие на очереди (PRPM ведёт). Subagents и Roles — пока Wild West; ждём конвергенции форматов.

Стек фреймворков

Deep Agents
Batteries included: planning, memory, skills, files
LangGraph
Orchestration: graphs, loops, state, persistence
LangChain
Foundation: models, tools, prompts, RAG
Слои, не конкуренты. Выбор верхнего уровня не отсекает нижние. LangGraph графы работают внутри Deep Agents, LangChain примитивы — везде. Deep Agents — одна из реализаций «batteries-included» уровня; аналоги: CrewAI, AutoGen, и IDE-встроенные агенты (Cursor, Windsurf).

Decision Guide

Вопрос Да →
Нужны подзадачи, файлы, память, skills? Deep Agents
Сложный control flow, loops, branching, HITL? LangGraph
Один агент: input → tools → output? LangChain
Чистый model call / RAG pipeline? LangChain LCEL
Mixing Layers

Типичная архитектура: Deep Agents оркестратор → LangGraph субагент для специфичного control flow → LangChain tools и retrievers как building blocks на каждом уровне.

Антипаттерны и ловушки

P0 — Runtime failures
  • HITL без checkpointer — crash; agent не может сохранить точку паузы
  • Забытый thread_id — каждый вызов = чистый стейт, контекст теряется
  • InMemorySaver в production — потеря всех данных при рестарте процесса
  • Side effects до interrupt() — дубликаты записей при каждом resume
P1 — Silent degradation
  • List без reducer — последняя запись тихо затирает предыдущие
  • Command + static edge — оба маршрута выполняются неочевидно
  • Vibe coding без Rules — неконтролируемый tech debt, заметен позже
  • PRD без acceptance criteria — невозможно определить «done»
  • AGENTS.md как Knowledge Base — context bloat, деградация качества
Архитектурные ошибки
  • Субагенты как stateful — они ephemeral by design
  • Skills наследуются субагентами — нет, указывайте явно
  • Один агент на всё — context bloat, потеря фокуса
  • Нет checkpoint перед ИИ-операцией — нет возможности отката
Правильные паттерны
  • Upsert (не insert) перед interrupt()
  • Side effects после interrupt()
  • Отдельные nodes для side effects
  • Explicit skills для каждого субагента
  • Rules < 50 строк, Skills < 500 строк
  • WIP-коммит → ИИ-операция → верификация

Дополнительные примитивы

Reflection

Самопроверка агента

Обязательный финальный проход, при котором агент критически оценивает собственный результат перед возвратом.

  • Проверка соответствия PRD
  • Поиск edge cases
  • Валидация constraints (Rules)
  • Оценка полноты решения
Reflection — не опция, а обязательный этап в production-grade agentic workflow.
Model Selection

Выбор модели под задачу

Не все задачи требуют самой мощной модели. Trade-off: стоимость, латентность, качество.

  • Fast — поиск, grep, простые правки. Низкая цена, высокая скорость
  • Default — стандартные задачи разработки
  • Capable — архитектурные решения, сложный рефакторинг, multi-step reasoning
Субагенты могут использовать разные модели. Explore-агент = fast, Code-review = capable.
Best-of-N

Параллельные попытки

Запуск N параллельных агентов в изолированных git worktrees. Каждый получает свою ветку и рабочую директорию.

  • Изолированный эксперимент
  • Сравнение N подходов
  • Выбор лучшего результата
  • Безопасное A/B тестирование решений
Каждый runner = своя ветка + worktree. Основной код не затрагивается.

Context Window — ограниченный ресурс

Контекстное окно — это конечный объём информации, которую агент может «помнить» в рамках одной сессии. Каждый загруженный файл, правило и skill конкурирует за это пространство.

Стратегии управления контекстом
  • Progressive Disclosure — загружай только то, что нужно сейчас
  • Subagent isolation — изолированный контекст на подзадачу
  • Skills on-demand — не greedily, а by necessity
  • Compact Rules — < 50 строк, одна забота на правило
  • TodoList — вместо удержания всего плана в промпте
Бюджет контекста
Элемент Загрузка Стоимость
System Prompt Всегда Высокая
AGENTS.md Всегда Средняя
Project Rules (always) Всегда Низкая*
Project Rules (glob) По файлу Низкая
Skills On-demand Средняя
Файлы проекта По запросу Переменная
История чата Накопительно Растёт

* при соблюдении < 50 строк на правило

Практика: Если агент «забывает» ранние инструкции — контекст переполнен. Делегируйте в субагент или разбейте на отдельные сессии с checkpoint-ами.

Матрица применимости

Сценарий Подход Обоснование
Прототип, демо, хакатон Vibe Coding Скорость важнее качества, одноразовый код
Новая фича в существующем проекте Agentic Coding + PRD + Rules Нужен контроль: стиль, архитектура, тесты
Большой рефакторинг Deep Agents + SubAgents + Checkpoints Много файлов, нужна декомпозиция, откат
CI/CD Pipeline с ИИ LangGraph + HITL Точный control flow, approval gates
RAG / Knowledge Base LangChain + Retrievers Стандартный pipeline, без сложной оркестрации
Safety-critical / Regulated НЕ вайб-кодинг Медицина, авионика, финансы — ручной контроль обязателен
Senior-правило: Вайб-кодинг — инструмент, не методология. Без Rules, PRD и Checkpoints он создаёт больше проблем, чем решает. С ними — кратно ускоряет разработку. Ваша задача как Senior+ — выбрать правильный уровень дисциплины для каждого контекста.

Ключевые выводы

  • PRD — не документация, а исполняемый контракт с чеклистом «done»
  • Rules — конституция проекта, < 50 строк, одна забота на правило
  • Skills — on-demand экспертиза, < 500 строк, progressive disclosure
  • Roles — инженер = архитектор + оркестратор + ревьюер, не prompt-writer
  • Subagents — stateless, изолированный контекст, явные skills
  • Checkpoints — двойной уровень: git WIP + agent state; дешевле переделки
  • HITL — обязателен для деструктивных операций; требует checkpointer + thread_id
  • Context Window — конечный ресурс; каждый токен должен оправдывать своё присутствие
  • Reflection — обязательный финальный проход; агент без самопроверки = неконтролируемый агент
  • Model Selection — fast для explore, capable для архитектуры; не все задачи требуют GPT-4.1
  • PEV — Plan → Execute → Verify как основной цикл agentic engineering
Вайб-кодинг + дисциплина = Agentic Engineering.
Разница между прототипом и production — в Rules, Checkpoints и HITL.
